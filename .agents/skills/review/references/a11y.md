# Checklist — accessibilité (RGAA 4.1.2 / WCAG 2.2 AA, via ultra11y)

Périmètre : tout `.tsx` du diff. Aucun → `skip — no UI files`.

egapro est une plateforme de l'État : RGAA 4.1.2 (106 critères), socle WCAG 2.2 AA. **ultra11y est l'unique dispositif** — pas de grille recopiée, pas de règles de mémoire. **Un audit fait de mémoire vaut moins que pas d'audit** : il produit des non-conformités inventées, exactement ce que le dispositif existe pour empêcher.

## Étape 1 — Contrôle de dérive du moteur (avant toute revue)

La référence est le tag épinglé de l'Action :

```bash
WANT=$(grep -m1 -E 'uses:[[:space:]]*SocialGouv/ultra11y@' .github/workflows/a11y.yaml | sed -E 's/.*#[[:space:]]*v([0-9.]+).*/\1/')
echo "dépôt: $WANT"
pnpm --filter app exec ultra11y --version          # devDependency — tenue par la CI, doit valoir $WANT
pnpm --filter app exec ultra11y status --project   # quels outils ont le hook câblé
```

Version du skill `review-a11y` que **ton outil** charge :

| Outil | Lire la version | Mettre à jour |
|---|---|---|
| Claude Code (plugin marketplace — seule copie que rien dans le dépôt n'épingle) | `python3 -c 'import json,os;print([e.get("version") for e in json.load(open(os.path.expanduser("~/.claude/plugins/installed_plugins.json")))["plugins"].get("ultra11y@ultra11y",[])])'` | `claude plugin marketplace update ultra11y && claude plugin update ultra11y --scope project`, puis redémarrer la session. Absent (le skill est introuvable) : `claude plugin install ultra11y@ultra11y`, une fois |
| OpenCode | rien à faire : `opencode.json` charge le plugin **et** ses skills depuis la devDependency `packages/app/node_modules/ultra11y`, donc toujours à la version épinglée | `pnpm install` si le plugin est introuvable, puis redémarrer |
| Codex | Codex ne lit les hooks et plugins qu'en portée utilisateur : `pnpm --filter app exec ultra11y status` | `pnpm --filter app exec ultra11y install --codex` (copie depuis la devDependency épinglée), à relancer après chaque bump |

- Version égale à `$WANT` → continuer.
- Version différente → **relire après la mise à jour** : `claude plugin update` monte au dernier tag de la marketplace, pas forcément au pin. Toujours différente → le dire dans le rapport (« revue faite avec ultra11y X, dépôt en Y ») et utiliser la voie CLI (étape 3b), qui tourne sur la devDependency épinglée.
- Constat historique : le plugin local a déjà dérivé de 4.5.1 alors que le dépôt était en 5.40.1 — une revue qui répond avec assurance à une autre question.

## Étape 2 — Ce que la machine garantit déjà (quel que soit le modèle)

| Couche | Quand | Ce qu'elle bloque |
|---|---|---|
| **pre-commit** (lefthook) | chaque `git commit` touchant un `.tsx` / `.jsx` / `.html` | `ultra11y audit src --jsx --graph --fail-on blocking` : constat bloquant du moteur, sur tout `src` (comme la gate CI) |
| **`pnpm verify`** | étape 5 de `/implement`, étape 2 de `/review gates` | le même audit statique de tout `src` |
| **CI `a11y-gate`** (`a11y.yaml`) | chaque PR, bloquant | audit statique JSX/TSX de tout `src`, `fail-on: blocking` — SARIF, annotations, commentaire sticky |
| **CI `a11y-lite`** (`a11y-lite.yaml`) | chaque PR vers `alpha`, bloquant | capture des pages que le diff peut changer, moteur seul : constat bloquant **nouveau** au rendu, route ni déclarée ni exemptée dans `packages/app/.ultra11yrc.json` (`require-sampled`), page sélectionnée non capturée |
| **CI `a11y-pages`** | cron lundi 04:00 UTC sur `alpha`, manuel | balayage complet + adjudication par modèle du reliquat. Mesure et publie, ne bloque pas sur les constats |

Plus, côté agent : le hook `PreToolUse` du plugin (Claude Code) / le plugin `ultra11y` (OpenCode) arrête un `git commit` / `git push` / `gh pr create` porteur de non-conformités. Coupe-circuits : `SKIP_A11Y=1` (une commande), `ULTRA11Y_HOOK=off` (une session), `"hook": { "failOn": "off" }` dans `.ultra11yrc.json` (le dépôt) — ne les utiliser qu'avec l'accord de l'utilisateur.

Ce que la machine **ne** voit **pas** et qui revient donc à cette revue : les **critères de jugement** (pertinence d'un `alt`, intitulé de lien en contexte, nom accessible vs libellé visible, logique clavier/focus d'un composant). Une régression de rendu sur un critère de jugement peut vivre jusqu'au cron du lundi.

Angles morts d'`a11y-lite`, à nommer en risque résiduel quand le diff les touche : il ne juge que les constats **nouveaux** (le backlog existant ne le fait pas rougir), et il ne capture que les pages que le graphe d'imports relie au diff. Un fichier qu'aucun import ne relie à une page mais qui change le rendu partout (layout racine, styles globaux, `middleware.ts`, config de build, dépendances DSFR) doit figurer dans `sample.global` de `packages/app/.ultra11yrc.json` — sinon aucune page n'est recapturée. Liste et raisons → `docs/accessibilite-ultra11y.md`, paragraphe `sample.global`.

## Étape 3 — La revue de jugement

**3a. Le skill `review-a11y` est disponible dans ton outil** → invoque-le sur la branche (`--since <BASE>`), et rends son rapport **tel quel**. Ne réimplémente rien : il cadre sur le diff, lance le moteur avec `--graph`, réfute les faux positifs avec preuve, tranche les critères de jugement depuis la source, et nomme les critères de rendu comme risques résiduels.

**3b. Skill absent** (ou plugin en dérive) → même méthode à la main, avec le moteur épinglé :

```bash
cd packages/app
pnpm exec ultra11y audit --since "${VERIFY_BASE:-origin/alpha}" --graph --json --lang fr > /tmp/a11y-review.json
```

Puis, pour chaque constat (`criteria`, `severity`, `file:line`, `message`, `remediation`) :
1. **Confirmer l'occurrence** : ouvrir la ligne citée ; l'élément fautif doit vraiment y être, dans le changement.
2. **Composants de bibliothèque (DSFR)** : une source propre peut produire un HTML cassé — le dire, recommander une vérification au rendu.
3. **Critères de jugement** : lire le composant **entier**, trancher avec une raison écrite.
4. **Réfuter** un constat exige une preuve citée dans le code. Écarter un constat en silence est interdit.
5. Garder le texte `remediation` du moteur comme base du correctif.

Règles du skill, à respecter dans les deux voies :
- **Ne jamais inventer** une non-conformité que le moteur n'a pas trouvée et que tu ne peux pas citer.
- **Revoir le changement, pas le monde** : un problème préexistant hors diff = une ligne finale, hors verdict.
- **Critères de rendu** (contraste 1.4.3, focus visible 2.4.7, zoom/reflow, contenu au survol) : toujours **risques résiduels** pour les composants changés, jamais déclarés conformes depuis la source. Ils se décident au rendu (`a11y-lite`, `a11y-pages`, `ultra11y scan`).
- Les jetons techniques restent en anglais dans la prose française : `aria-live`, `tabindex`, `alt`, `role="alert"`.

Correctifs mécaniques sûrs (opt-in, hors mode gates qui est lecture seule) : `pnpm --filter app exec ultra11y fix --staged --write --safe`.

## Écrire accessible (rappel pour le correctif)

Les règles par critère se demandent au moteur, pas à la mémoire : `pnpm --filter app exec ultra11y criteria --standard rgaa 8.3`, `criteria --standard rgaa --glossary <terme>`. Principe unique : **HTML natif d'abord, ARIA en dernier** — un `<button>` plutôt qu'un `<div role="button">` ; ne jamais doubler une sémantique implicite (`role="navigation"` sur `<nav>` est faux, pas redondant).

## Ce qui n'est PAS le dispositif

- **Lighthouse** : score d'accessibilité en `warn` seulement ; sa notion n'est pas celle des 106 critères.
- **`scripts/quality/check-patterns.sh`** : interdit `<img>` brut, `<svg>` inline, `style={}`, les couleurs en dur — règles DSFR et Next qui servent aussi l'accessibilité, pas un tier d'accessibilité.
- **`structural.md`** : ne rapporte rien sur l'accessibilité, délibérément.

## La version vit à plusieurs endroits

| Où | Quoi | Tenu par |
|---|---|---|
| chaque `uses:` des workflows (`a11y.yaml` ×2, `a11y-lite.yaml` ×2) | le moteur de la CI | `a11y-version-coherence` (`ci.yaml`) via `scripts/a11y/check-ultra11y-version.sh` |
| `packages/app/package.json` (devDependency) | le binaire et le plugin Playwright qui **écrivent** les instantanés ; le moteur de pre-commit et de `pnpm verify` | idem |
| le plugin / les skills de l'outil IA | `review-a11y`, donc cette revue | étape 1 ci-dessus |

Les deux premières doivent être identiques : la suite Playwright écrit les instantanés avec la devDependency, l'Action les réingère avec son moteur. Deux versions = deux formats, et la divergence ne lève aucune erreur — elle se lit comme des critères « à évaluer » dans un rapport qui a l'air complet. Dependabot propose `github-actions` et `npm` à la même cadence (lundi 01:00) pour que les deux PR arrivent ensemble ; la CI refuse une demi-montée.

- **Ne retire pas la devDependency `ultra11y`** parce qu'aucun `import` ne la cite : c'est le binaire (`pnpm exec ultra11y`) et le plugin Playwright (`ultra11y/playwright`, utilisé par `src/e2e/a11y/`).
- **Ne remets pas `@axe-core/playwright`**, retirée volontairement : deux copies de Playwright dans un même process se rendent des `Page` que les fixtures de l'autre ne reconnaissent pas.

Câblage CI complet, coûts, registre de verdicts, `undecidable.json`, procédure de bump → [`docs/accessibilite-ultra11y.md`](../../../../docs/accessibilite-ultra11y.md). À lire avant de toucher à `a11y.yaml` ou à la version.

## Sortie

Le rapport `review-a11y` (ou son équivalent 3b) : 🔴 bloquant / 🟠 majeur / 🟡 mineur avec `fichier:ligne — critère — constat → correctif`, puis **Risques résiduels**, puis le verdict :

- `PASS` — aucune non-conformité (des risques résiduels peuvent rester, nommés).
- `NEEDS WORK` — au moins une non-conformité bloquante.
- `MINOR` — seulement des non-conformités majeures ou mineures.
